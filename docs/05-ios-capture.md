## 5. 一个刻意的决定：先用 Swift 5 语言模式

Xcode 27 默认倾向 Swift 6 严格并发。M1 没有并发代码，但 M2 会引入
`ARSessionDelegate` 回调（后台线程）+ `@Published` 状态（主线程），
那才是真正需要处理 `Sendable` / actor 隔离的地方。

现在的选择是**显式固定 `SWIFT_VERSION = 5.0`**，把并发迁移推迟到 M2 一并做，
避免在还没有并发代码时先制造一套不成熟的隔离模型。
这不是"忘记升级"，是排期。

## 7. M2-a：采集格式实测（已实现，待真机验证）

M2 的第一步**不是**写编码和上传，而是把格式量出来。因为
`supportsFrameSemantics(.sceneDepth)` 只回答"支不支持"，不回答"多大、什么格式"。

### 7.1 做了什么

新增 Tab「采集实测」，启动 `ARWorldTrackingConfiguration`（`frameSemantics = [.sceneDepth]`），
把**同一个 `ARFrame`** 里的以下数值实时显示并支持一键复制：

| 组 | 内容 |
|---|---|
| 运行 | 帧序号、跟踪状态、实测 FPS |
| RGB | 分辨率、像素格式、plane 数、每个 plane 的 bytesPerRow |
| 深度 | 分辨率、像素格式、bytesPerRow、有效像素比例、深度范围（米） |
| 置信度 | 分辨率、像素格式、bytesPerRow |
| 内参 | fx / fy / cx / cy、参考分辨率 |
| 对齐 | 深度/RGB 缩放比、宽高比是否一致 |

### 7.2 三个刻意的实现选择

1. **像素格式用系统常量匹配，不靠 fourCC 字符串记忆**。
   `PixelFormatName.describe` 里是 `case kCVPixelFormatType_DepthFloat32:` 这类分支，
   认不出的才回退到打印 fourCC。这样显示的名字不可能因为记忆错误而错。
2. **深度采样只在 float32 格式下进行**。其他格式直接返回"未采样"，
   绝不按猜测的内存布局去读——读错内存比读不到更糟。
3. **预览用 ARSCNView**，不自己做 YUV→RGB。M2-a 只需确认"会话真的在出图"，
   YUV 转换是 M2-b 的活，不应提前混进来。

### 7.3 实测结果（两次独立运行）

| 项 | 第一次 | 第二次 |
|---|---|---|
| RGB | 1920×1440 `420YpCbCr8BiPlanarFullRange`，2 plane，bpr=[1920, 1920] | 同左 |
| 深度 | 256×192 `DepthFloat32`，bpr=1024 | 同左 |
| 置信度 | 256×192 `OneComponent8`，bpr=256 | 同左 |
| 深度范围 | 0.190–2.883 m，有效 100% | 0.162–2.936 m，有效 100% |
| 深度/RGB 缩放 | 0.1333（= 1/7.5），宽高比一致 | 同左 |
| FPS | 30.0 | 30.0 |

结论：`bytesPerRow` 恰好都等于「宽度×每像素字节数」，即**无 padding**；
但代码仍按 `bytesPerRow` 走，不依赖这个巧合。

### 7.4 重要发现：内参不是常量

| 参数 | 第一次 | 第二次 | 变化 |
|---|---|---|---|
| fx = fy | 1474.81 | 1487.42 | +0.86% |
| cx | 932.79 | 935.89 | +3.1 px |
| cy | 719.97 | 712.43 | −7.5 px |

自动对焦会改变焦距（focus breathing），ARKit 的动态标定也会微调主点。
**因此内参必须逐帧记录，不能在启动时取一次复用。**

0.86% 的焦距误差在 0.5 m 处约等于 4 mm 的横向偏差——对 2 cm 的落石是不可忽略的比例。
`frame_bundle` 契约本来就是逐帧内参字段，但实现上必须真的按帧写。

### 7.5 这一版要回答的问题

- 深度图真实分辨率是多少？（文档说 256×192，但 iOS 27 上没实测过）
- 深度像素格式是 `DepthFloat32` 还是 `DisparityFloat32`？
- RGB 是几个 plane？每 plane 的 bytesPerRow 是多少？
- `camera.intrinsics` 的参考分辨率是不是 1920×1440？
- 深度与 RGB 的宽高比是否一致（决定 M5 能否按比例缩放）？

回答完这些，M2-b（YUV→RGB + JPEG）才有依据。

## 8. M2-b：RGB 转码与编码（已实现，待真机目视校验）

### 8.1 做了什么

| 文件 | 职责 |
|---|---|
| `YUVConverter.swift` | vImage 显式转换 `420YpCbCr8BiPlanar → BGRA` |
| `FrameEncoder.swift` | 转 CGImage / UIImage，并做 JPEG 编码，统计耗时与体积 |

界面上把 **ARKit 自己渲染的画面** 与 **vImage 转出来的画面** 并排显示，
颜色一致才算转码正确。

### 8.2 三个关键实现点

1. **显式使用 `bytesPerRow` 建 `vImage_Buffer`**，而不是假设行跨度等于宽度。
   实测这台设备恰好无 padding（1920 / 1920 / 1024 / 256），但代码不能依赖这个巧合。
2. **颜色矩阵与取值范围都不猜**：
   - 取值范围由像素格式决定（`FullRange` vs `VideoRange`）；
   - 矩阵优先读 CoreVideo 附件 `kCVImageBufferYCbCrMatrixKey`，读不到才回退 BT.709。
3. **通道重排 `[3,2,1,0]`**：vImage 输出的是内存序 A,R,G,B；
   CGImage 用 `byteOrder32Little + noneSkipFirst` 需要 B,G,R,A。

### 8.3 不阻塞 ARSession

编码放在独立串行队列 `com.mountain.roadcapture.encoder`，并且：
- 每 0.5 s 才触发一次（M2-b 是校验阶段，不需要满帧率）；
- 用 `NSLock` 保护的 `encodeInFlight` 做背压：上一帧还没编完就**直接跳过**，
  宁可少一帧也不在队列里堆积；
- 闭包同时持有 `ARFrame`：ARKit 的像素缓冲生命周期绑定在 ARFrame 上，
  只保留 `CVPixelBuffer` 在极端情况下可能遇到缓冲被回收。

### 8.4 要目视确认的两件事

1. **颜色**：左右两张图的色调应基本一致。若左边正常、右边偏绿/偏紫，
   说明矩阵或通道重排错了。
2. **方向**：`capturedImage` 原生是 landscape-right，
   竖屏下若显示为横躺，说明 `UIImage.Orientation` 选错，改 `.right` / `.up` 即可。

这两项只能靠眼睛看，代码层面无法自证。

### 8.5 真机校验结果（2026-11-05）

| 校验项 | 结果 |
|---|---|
| 颜色 | ✅ 与 ARKit 预览色调一致 |
| 方向 | ✅ 正向，与预览一致 |
| YUV→BGRA | **1.29 ms** |
| JPEG 编码 | **31.26 ms** |
| JPEG 体积 | **468 KB**（q=0.72） |

单帧合计约 32.5 ms。10 FPS 下约占单核 1/3，能跑但无冗余——
M2-c 若实测持续丢帧，退路是降到 1280×960 或改用硬件 `VTCompressionSession`。

### 8.6 未做

- 编码结果**不落盘、不上传**，只用于测量与显示；
- JPEG 的最终方向与命名（是否烘焙旋转）留给 M4 打包时决定。

## 9. M2-c：节流、原始拷贝与资源观测（已实现，待真机稳定性验证）

### 9.1 节流

原生 30 fps，目标 10 fps。实现上按**时间间隔**抽帧，而不是"每 3 帧取 1 帧"：

```swift
guard frame.timestamp - lastCaptureTimestamp >= captureInterval * 0.9 else { skip }
```

那个 `0.9` 不是随手写的。3 × 33.33 ms = **99.99 ms**，比 100 ms 差一点点，
严格比较会直接掉到每 4 帧取 1 帧，实测只有 **7.5 fps**。
留 10% 容差后，每 3 帧稳定取 1 帧。

按间隔而不是按帧号计数，是因为原生帧率可能随设备/视频格式变化；
按时间抽帧对 30 fps 和 60 fps 都成立。

### 9.2 原始拷贝

| 数据 | 大小 | 方式 |
|---|---|---|
| 深度 | 196 KB | `float32`，**按 `bytesPerRow` 整块拷**，保留原始行跨度 |
| 置信度 | 49 KB | `uint8`，同上 |

拷贝保留 padding（如果有），下游用 `bytesPerRow` 解读，不做"假设紧凑"的优化。

**验证拷贝保真的办法**：深度统计（有效比例、最小/最大值）现在**从拷贝出来的 `Data` 上算**，
而不是从 `CVPixelBuffer` 上算。如果拷贝损坏，统计会立刻异常。

### 9.3 背压与内存

- 编码在独立串行队列，`NSLock` 保护的 `encodeInFlight`：上一帧没编完就**直接丢帧并计数**，
  不在队列里堆积。
- 每次采集用 `autoreleasepool` 包裹，临时对象及时释放。
- `MemoryProbe` 读 `mach_task_basic_info.resident_size`，记录常驻与峰值（加锁，避免跨队列竞争）。

### 9.4 观测指标

界面新增「采集节流（M2-c）」分组：

| 指标 | 期望 |
|---|---|
| 实测采集 FPS | ≈ 10（不是 30） |
| 节流跳过 | ≈ 2 × 已产出帧（30 → 10 意味着丢掉 2/3） |
| 编码繁忙丢帧 | **0**（若 > 0 说明编码跟不上，需降分辨率或换硬件编码） |
| 深度/置信度拷贝 | 各 < 1 ms |
| 内存 常驻/峰值 | 运行数分钟后**应趋于平稳**，不应持续上涨 |

### 9.5 真机验证结果（235 s 连续运行）

| 指标 | 期望 | 实测 | 判定 |
|---|---|---|---|
| 实测采集 FPS | ≈ 10 | **10.0** | ✅ |
| 编码繁忙丢帧 | 0 | **2 / 2340**（0.085%） | ✅ 可忽略 |
| 深度拷贝 | < 1 ms | 0.166 ms / 192 KB | ✅ |
| 置信度拷贝 | < 1 ms | 0.015 ms / 48 KB | ✅ |
| JPEG 编码 | — | 28.98 ms / 414 KB | ✅ |
| 原生 FPS | 30 | **20** | ⚠️ 掉帧 |
| 内存 | 平稳 | 起始— / 当前 279.3 / 峰值 365.1 MB | ❓ 单点无法判定 |

#### 关键发现：原生帧率会掉，时间抽帧救了场

前几次短测原生都是 30 fps，连续运行 4 分钟后掉到 **20 fps**
（5757 帧 / 235 s ≈ 24.5 fps 平均，说明是逐渐下降的），大概率是热压力下 ARKit 降帧。

如果按"每 3 帧取 1 帧"实现，20 fps 原生下只能得到 **6.67 fps**，采集率直接崩掉。
按时间间隔抽帧后，原生 30 → 20 的变化对采集率完全无影响，实测仍是 10.0 fps。

**这条把 §9.1 的设计选择从"看起来合理"变成了"被数据证明必要"。**

#### 内参漂移的幅度被低估了

| | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| fx | 1474.81 | 1487.42 | 1473.48 |
| cx | 932.79 | 935.89 | **971.84** |
| cy | 719.97 | 712.43 | **683.66** |

主点相对画面中心（960, 720）的偏移在三次运行中达到 **±25 / ±36 px**。
`frame_bundle` 的逐帧内参不是形式主义，是必须。

### 9.6 内存趋势（本轮新增）

单点快照无法区分"正常波动"和"缓慢泄漏"，因此增加时间序列：

- 每 5 s 采样一次，保留最近 24 个点（约 2 分钟窗口）；
- 输出「起始 / 当前 / 峰值」与「变化 = 当前 − 起始」；
- 判据：`变化` 持续为正且单调上升 → 泄漏；在一个区间内来回波动 → 正常。

### 9.7 热压力已确认

第 3 轮运行（245 s）读数：

```
热状态: 严重过热   原生FPS: 20.0   低电量模式: 关
```

原生帧率从 30 掉到 20 **不是偶发**，是持续负载下的热降频。
这意味着 M7 之前必须定下主动降帧策略（例如 `thermalState == .serious` 时把目标 FPS 降到 5）。

### 9.8 一次由自己引入的回归（已修复）

M2-b 阶段 JPEG 编码是 **2 Hz**（只为预览），编码丢帧 2 次。
M2-c 我把编码改成**跟采集同频 10 Hz**，理由是"10 fps 全链路更完整"——这是错的。

| | M2-b（2 Hz 预览） | M2-c（10 Hz 预览） |
|---|---|---|
| 每帧 BGRA 缓冲 | 11 MB | 11 MB |
| 分配速率 | 22 MB/s | **110 MB/s** |
| 编码繁忙丢帧 | 2 | **377（15.7%）** |

根因：**把"预览刷新率"和"采集率"绑在了一起**。预览是给人看的，2 Hz 足够；
11 MB 的 BGRA 每秒创建 10 个，在热降频下编码队列必然追不上。

修复：
1. RGB 转码/编码恢复为 `previewInterval = 0.5 s`，与 10 Hz 采集解耦；
2. 预览只保留 **640×480 缩略图**，不再长期持有整幅 11 MB 的 BGRA。

> 教训：测量项本身也会改变被测量的系统。加一个"为了更完整"的采集率提升，
> 结果把一个通过的状态改成了不通过。

### 9.9 第 4 轮：丢帧归零，内存无泄漏证据

| 指标 | 实测 | 判定 |
|---|---|---|
| 编码繁忙丢帧 | **0** | ✅ 2 Hz 预览 + 10 Hz 采集配比正确 |
| 内存 | 114 → … → 334 → **278** → 297 | ✅ 有回收，非无界泄漏 |

内存序列（每 5 s，MB）：

```
114 → 250 → 264 → 269 → 272 → 274 → 278 → 278 → 278 → 303 → 300 → 310
→ 311 → 311 → 312 → 312 → 312 → 313 → 314 → 314 → 318 → 334 → 278 → 297
```

判读要点：末尾 **334 → 278** 是一次 56 MB 的回收。**泄漏不会自己退回去**，
这是典型的"管线初始化 + 建图增长 + 系统回收"，不是持续泄漏。
前期 114→250 是 ARKit 拉起相机与深度管线的一次性成本。

### 9.10 热归因必须打折

第 3、4 轮都读到 `热状态: 严重过热`、原生 30→20 fps。但设备当时**同时开着 5G 与个人热点**，
5G 基带与热点转发本身就是主要热源之一，iPhone 12 系列的散热设计也偏紧。

因此只能说：**观测到过热与降帧同现，但热源不唯一，不能归因于采集管线。**
要定论需要一次干净对照（关闭 5G 与热点、屏幕常亮、跑 3 分钟）。

同期观测到的性能数字（转码 11.40 ms、编码 43.81 ms，约为上一轮的 13 倍 / 1.6 倍）
同样被热污染，**不可作为基线**。

### 9.11 内参漂移的完整区间

| 参数 | 最小 | 最大 | 波动 |
|---|---|---|---|
| fx = fy | 1464.57 | 1506.89 | **2.9%** |
| cx | 930.94 | 971.84 | 41 px |

## 10. M3：深度与置信度伪彩色（已实现，待真机确认）

### 10.1 为什么可视化不只是"好看"

渲染输入是 **M2-c 拷贝出来的 `RawPlane`**，不是 `CVPixelBuffer`。
也就是说：如果拷贝链路有任何问题（行跨度错、字节序错、截断），
伪彩色画面会立刻变形或出现错位条纹。

**可视化在这一步同时承担了数据完整性校验的职责。**

### 10.2 实现

| 文件 | 职责 |
|---|---|
| `RawPlane.swift` | 平面拷贝的公共模型，保留 `bytesPerRow` |
| `Visualizers.swift` | 深度/置信度 → `CGImage` |

- **深度**：固定色标 **0.2–3.0 m**（不是逐帧自适应，否则不同时刻颜色无法比较）。
  近红 → 黄 → 绿 → 青 → 远蓝；无效像素为**纯黑**，与"很远"的深蓝区分开。
- **置信度**：`ARConfidenceLevel` 三档 → 低=红 / 中=黄 / 高=绿，未知=灰。
- 显示用 `.interpolation(.none)`：**故意让 256×192 的马赛克可见**，
  不掩盖"深度只有 256 宽"这个事实。

### 10.3 首轮发现的问题与修复

深度与置信度图相对 RGB **横躺 90°**。原因：`capturedImage` 是 landscape-right，
RGB 用 `UIImage.Orientation.right` 纠正了，而伪彩色 CGImage 是裸图、不带方向信息。
修复：两张伪彩图同样带 `.right`。

> 三个视图的方向处理必须同源，否则"看起来对不齐"会被误判成数据对齐问题。

### 10.4 真机要看什么

1. **深度色彩是否随距离变化**：近处偏红、远处偏蓝，桌面/地面应有连续渐变。
2. **场景是否与 RGB 对得上**：桌沿、椅子等轮廓应出现在相同位置——证明同帧。
3. **置信度是否大部分为绿**：边缘、反光、远景出现黄/红是正常的。
4. **黑色区域**：代表无效深度。之前实测有效率 100%，若大量出现需排查。

### 10.4 未做

- 不做深度值的逐像素数值显示（M4 打包时会以原始 Float32 保存，不做可视化有损转换）；
- 不做点云或 3D 视图。

## 12. 这批真机数据回答的三个问题

### 12.1 置信度经验性地标出了 LiDAR 的有效量程

同一帧内按深度分桶统计置信度（frame_0011）：

| 深度区间 | 低 | 中 | 高 |
|---|---|---|---|
| 0.00–0.10 m | **99%** | 1% | 0% |
| 0.10–0.20 m | **97%** | 3% | 0% |
| 0.20–0.30 m | 36% | 24% | 39% |
| 0.30–0.40 m | 25% | 14% | 61% |
| 0.40–3.00 m | 0% | 0% | **100%** |

结论：**LiDAR 的可靠近界约在 0.2–0.3 m**，0.4 m 以外几乎全部高置信度。

这解释了为什么 Python 侧 `DepthPolicy.min_range_m = 0.20` 是合理的，
同时也说明**光靠量程门控不够**——0.20–0.30 m 区间里有 36% 是低置信度，
必须由 confidenceMap 这一层筛掉。两道门都要保留。

沙盘预期拍摄距离 0.4–0.8 m，正好落在"100% 高置信度"区间，是好消息。

### 12.2 内参漂移是自动对焦收敛，不是随机抖动

20 帧（2 秒）内的 fx 序列：

```
983.0 → 987.6 → 992.6 → 996.3 → 1000.0 → 1002.7 → 1005.1 → 1009.0
→ 1013.6 → 1018.5 → 1021.6 → 1021.57 → … → 1021.66
```

**前 11 帧单调上升 3.93%，第 12 帧起稳定到小数第三位。**

同时跟踪状态在第 6 帧从 `limited_initializing` 变为 `normal`。

这修正了 §9.11 的解释：不是"ARKit 动态标定随机漂移"，而是**自动对焦从无穷远收敛到
约 0.2 m 的近距离物体**，焦距随之变化，锁定后即稳定。

工程含义：**会话开始约 1 秒内的内参不可用于米制计算。**

### 12.3 深度在近距离非常平滑

邻域深度跳变 >10 cm 的比例：横向 **0.0%**、纵向 **0.0%**。
画面是近距离平面物体，深度无噪声条纹，说明数据本身是干净的——
之前看到的"浅色、低置信度"是量程问题，不是解码问题。
