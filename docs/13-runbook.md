> 照着从上往下做即可。每一步都写了「你应该看到什么」，对不上就跳到第 6 节。

## 0. 系统由什么组成

| 组件 | 在哪 | 作用 |
|---|---|---|
| 后端 (FastAPI) | 电脑 | 收数据、存数据、推状态、提供网页 |
| AI worker | 电脑 | 跑模型，把感知结果回传给后端 |
| 网页 | 浏览器 | 看状态（用户端 + 管理后台） |
| App | iPhone | 采集 RGB + 深度并上传 |

**四个部分缺一不可。** 手机不在线，网页就一直显示「数据已过期」。

## 2. 启动（每次开机后）

### 2.1 双击启动（推荐）

在项目文件夹里双击：

| 文件 | 作用 |
|---|---|
| **启动系统.command** | 启动后端 + AI worker，并自动打开浏览器 |
| **停止系统.command** | 停止全部服务 |

## 6. 出问题怎么办

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| `缺少 Python 环境` | venv 没建 | `bash scripts/bootstrap_mac.sh` |
| `风险引擎编译失败` | 缺 CMake / 编译器 | 看 `data/logs/build_engine.log` |
| 网页打不开 | 后端没起 | `bash scripts/status.sh` 看状态 |
| 网页显示「后端不可达」 | 端口不对 / 后端崩溃 | 看 `data/logs/backend.log` |
| 手机「服务器不可达」 | IP 变了 / 不在同一网络 | 重新看 `start_all.sh` 输出的 IP |
| 状态流一直「连接中…」 | WebSocket 被防火墙拦 | 检查 Mac 防火墙，或换热点 |
| 一直「数据已过期」 | 手机没在采集 / AI worker 挂了 | 看 `/admin` 里 AI Worker 状态 |
| AI worker 显示「停滞」 | worker 进程挂了 | `tail -50 data/logs/ai_worker.log` |
| 事件页截图显示「已清理」 | 超出保留窗口（24h） | 正常现象，数据已按策略删除 |
| 深度图纯黑 | 手机没拿到 LiDAR 深度 | 确认是带 LiDAR 的机型，且距离 >0.2 m |

### 看日志

```bash
tail -50 data/logs/backend.log     # 后端
tail -50 data/logs/ai_worker.log   # AI worker
```

### 前后端一键自检

```bash
perception/.venv/bin/python scripts/smoke_test_backend.py
```

**应看到**：`全部通过 (10/10)`。

## 7. 数据在哪、怎么清理

| 内容 | 位置 | 说明 |
|---|---|---|
| 数据库 | `data/db/mountain.db` | 帧、判定、事件、设备 |
| 原始帧 | `data/artifacts/<frame_id>/` | 每帧 4 个文件 |
| 日志 | `data/logs/` | 后端 / worker 日志 |
| 进程号 | `data/run/` | 启停脚本用 |

### 保留策略（两套，互不影响）

| 内容 | 默认保留 | 环境变量 | 说明 |
|---|---|---|---|
| 数据库记录 | 24 小时 | `ROAD_RETENTION_HOURS` | 判定、事件、帧元数据 |
| **原始帧文件** | **30 分钟** | `ROAD_ARTIFACT_HOURS` | 图像/深度，**体积增长极快** |

**为什么原始文件只留 30 分钟**：

```
10 fps × 约 340 KB/帧 ≈ 3.4 MB/s ≈ 12 GB/小时
```

实测两小时测试就攒了 **672 MB**。如果按 24 小时留，会到 **280 GB**。

文件清理有三条豁免规则（都有测试覆盖）：

1. **还没被 AI 处理的帧** —— 删了 worker 就读不到
2. **被落石事件引用的帧** —— 事件截图要能看
3. 其余按时间清理；数据库行保留，历史表格里仍能看到记录

调整：`ROAD_ARTIFACT_HOURS=2 bash scripts/start_all.sh`（约 24 GB，注意磁盘）

### 彻底重置（清空所有历史）

```bash
bash scripts/stop_all.sh
rm -rf data/db/mountain.db* data/artifacts/*
bash scripts/start_all.sh
```

> 建议在正式沙盘实验前重置一次，避免测试数据混进历史曲线。

## 附录 A：俯视跟踪测试（不需要沙盘）

**目的**：确认手机垂直向下看时，ARKit 还能稳定跟踪。跟踪一旦失效，
所有米制结论都不成立——这是唯一还没排除的结构性风险。

### A1. 架设

- 镜头**垂直向下**，高度约 **0.64 m**（可用书本叠到该高度）
- 手机要固定住，测试过程中**不能碰**
- 注意：摄像头在机身一角，架设时让镜头对准桌面中央

### A2. 测试两轮

| 轮次 | 桌面状态 | 意义 |
|---|---|---|
| 第 1 轮 | 原始桌面（可能很光滑） | 最坏情况 |
| 第 2 轮 | 铺一块有纹理的东西（布、书封面、打印的图案） | 接近沙盘表面 |

每轮 60 秒。

### A3. 操作

```bash
bash scripts/start_all.sh        # 确保服务在跑
```

1. 手机填电脑 IP → 测试连接 → 开始
2. 静置 60 秒，不要碰手机
3. 看诊断里的这几行：

| 行 | 通过标准 |
|---|---|
| 跟踪 | 稳定「正常」，不频繁掉到「受限」 |
| Depth 采样 | 有效率高（>80%），范围约 0.60–0.70 m |
| 端到端风险 | 有数据（UNKNOWN 正常） |
| 队列 | 0 / 32 |

4. 停止采集，把诊断文本整段复制下来

### A4. 判读

- **两轮都正常** → 机位可行，可以做深度标定
- **光滑桌面失败、有纹理成功** → 沙盘表面必须有纹理，需在沙盘制作时考虑
- **两轮都失败** → 俯视方案不可行，需要改变机位或增加人工标记

## 附录 B：深度精度标定

**目的**：验证 LiDAR 读数的**米制精度**。此前只验证过"深度与 RGB 对齐"，
从没验证过"深度值准不准"。

### B1. 准备

- 手机按 **0.64 m 垂直向下**架好（与正式使用一致）
- 找一个**平顶、厚度均匀**的物体：厚书、字典、快递盒
- 用直尺量出它的实际厚度（多次测量取中位数，记到毫米）

### B2. 操作

1. 把物体放在**画面正中央**
2. App 里开始采集，保持 3 秒，停止
3. 在电脑上运行：

```bash
perception/.venv/bin/python scripts/measure_depth_step.py --latest --height-mm 20
```

把 `--height-mm` 换成你量到的实际厚度。

### B3. 判读

输出类似：

```
中心深度     600.2 mm  (IQR 4.1 mm, 有效 100%)
外围深度     620.5 mm  (IQR 3.8 mm, 有效 100%)
测得台阶      20.3 mm
实际台阶      20.0 mm
误差          +0.3 mm  (+1.5%)
结论          精度良好（±3 mm 内）
```

| 误差 | 结论 |
|---|---|
| ±3 mm 内 | 精度良好，米制结论可直接使用 |
| ±3–8 mm | 可接受，但结论应保留 1 cm 以上余量 |
| > ±8 mm | 米制结论不可信，需检查安装距离或遮挡 |

### B4. 建议做三组

用不同厚度（如 10 / 20 / 40 mm）各测一次，才能看出误差是否随高度线性增长。

### B5. 常见问题

| 现象 | 原因 |
|---|---|
| IQR 很大（>30 mm） | 中心区域没被物体占满，或表面不平 |
| 有效像素低 | 距离太近（<0.2 m 时 LiDAR 不可靠）或有镜面反射 |
| 测得台阶明显小于实际 | 物体没有完全落在中心区域内，改大 `--center` 或调整位置 |
